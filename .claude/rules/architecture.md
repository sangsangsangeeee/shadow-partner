# 무엇을 어디에 두는가

## 두 칸

**`commons/`는 이 화면을 몰라야 한다.** 콤보·라운드·호출어라는 말이 나오면 거기 있으면 안 된다.
`Overlay`는 commons에 있고 `MovePickerSheet`는 screens에 있는 이유가 이거다.

**`screens/ShadowCoach/`는 이 앱의 말을 쓴다.** 도메인이 스며든 건 전부 여기.

경계가 헷갈리면 이렇게 물어라 — *다른 화면을 하나 더 만들면 이걸 그대로 쓸 수 있나?*

## screens 안의 세 칸

| | 무엇 | 판단 기준 |
|---|---|---|
| `hooks/` | 상태와 그 전이 | 렌더를 하지 않는다 |
| `views/` | 탭 하나가 통째로 | `index.tsx`가 셋 중 하나를 고른다 |
| `parts/` | 뷰가 쓰는 조각 | 카드·줄·오버레이·시트 |

`index.tsx`에 남는 건 **조립뿐이다.** 세 훅을 부르고, 탭에 맞는 뷰를 고르고,
떠 있는 층(FAB·토스트·탭바)을 얹는다. 여기서 도메인 로직이 자라기 시작하면 훅으로 내려보내라.

## 하위 화면은 바텀시트다

**라우트는 `/` 하나뿐이다.** 갔다가 돌아오는 화면은 전부 TDS 바텀시트로 띄운다.

고를 것이 셋 있었고, 이 순서로 결론이 났다:

| | 왜 아닌가 |
|---|---|
| 겹침(RN `Modal`) | **별도 네이티브 층이라 토스 상태바를 덮는다.** 토스는 그 헤더를 숨길 길을 안 준다 |
| 라우트 | 문제는 풀리지만 값을 문다 — 결과를 못 들고 오고, 자료가 트리 밖으로 나가고, 전환마다 손볼 게 생긴다 |
| **바텀시트** | `Modal`이 아니라 앱 트리 안의 `position:absolute` 뷰다. 헤더를 안 덮으면서 위 값도 안 문다 |

핵심은 **문제가 "겹침"이 아니라 "네이티브 층"이었다**는 것이다. 새 하위 화면이 필요하면
라우트를 파기 전에 시트로 되는지부터 보라. 전체 화면은 훈련 완료 하나만 남는다 —
나가는 길을 우리가 정하는 화면이라 뒤로가기가 있으면 안 된다. 거기만 `Overlay`(Modal 포장)를 쓴다.

**시트를 띄우면 떠 있는 층을 걷어라.** TDS 시트는 z를 걸지 않아서 탭바(z 40)와 FAB(z 30)가
그 위로 올라온다. `anySheetOpen`으로 셋을 함께 본다 — 하나만 보면 나머지 둘에서 뚫린다.

시트 부품은 `screens/ShadowCoach/parts/`에 둔다. 자기 초안 상태는 자기가 들고 있되,
**닫힐 때 되감아라** — 시트는 닫혀도 트리에 남아서 지난 입력이 다음에 그대로 보인다.

## 배럴

폴더마다 `index.ts`로 내보낸다. 바깥에서는 배럴만 가리킨다.

```ts
import { Overlay, Segmented, Typo } from '../../commons/components';   // 좋음
import { Overlay } from '../../commons/components/Overlay';            // 나쁨
```

## 새 조각을 만들기 전에

**패턴을 먼저 올려라.** 같은 렌더가 세 곳에 있으면, 세 곳을 각각 컴포넌트로 자르지 말고
그 패턴을 `commons/components`로 승격시켜라. `Segmented`는 12줄짜리 map이 네 벌 있어서 생겼고,
`Overlay`는 네 개의 모달이 같은 뼈대(머리·스크롤 몸통·고정 발)를 갖고 있어서 생겼다.

순서를 뒤집으면 공유 스타일이 복제된다. **패턴 승격이 먼저, 컴포넌트 분리가 나중.**

**쓰는 곳이 줄면 도로 내려라.** 그 넷 중 셋이 시트로 내려가면서 `Overlay`는 호출부가 하나만 남았고,
머리·`avoidKeyboard`·`headExtra` 갈래가 전부 죽은 코드가 됐다. 갈래를 걷어내 완료 화면 모양만 남겼다.
같이 죽은 `PillButton`(46줄)은 지웠다 — **승격의 근거가 사라지면 승격도 되돌린다.**

## 자를지 말지

줄 수로 정하지 마라. 실제로 재본다:

- 그 구역이 화면 스코프의 식별자를 **몇 개** 쓰는가
- 잘라내면 prop이 몇 개가 되는가

prop이 열 개를 넘어가면 대개 잘못 자른 것이다. 두 가지 처방이 있다:

1. **훅 결과 객체를 통째로 넘긴다.** `TrainView`는 `training`과 `callouts`를 그대로 받아
   prop 14개를 2개로 줄였다.
2. **그 뷰만 쓰는 상태는 뷰로 내린다.** `expandedId` `editingId` `highlight` `scrollRef`는
   화면이 아니라 뷰가 갖는다.

## 변하는 중인 모양 위에 추상을 얹지 마라

중복이 셋 보인다고 바로 묶지 마라. 먼저 물어라 — **그중 하나가 곧 달라지나?**

떠 있는 층의 `bottom` 계산이 그랬다. 세 곳이 같은 식을 쓰고 있었지만
TDS Toast 교체가 예정돼 있었고, Toast는 안전영역을 스스로 더해서 식의 모양이 달라진다.
미리 묶었다면 추상을 만들고, 한 호출부가 어긋나고, 억지로 늘리거나 도로 푸는 일을 했을 것이다.
미루고 나니 남은 게 2곳이라 묶을 이유 자체가 사라졌다.

**이건 "정리를 미룬다"는 뜻이 아니다.** 지금 실제로 비용을 물리는 구조 문제는 즉시 한다.
판단 기준은 시간이 아니라 **그 모양이 안정됐는가**다.
